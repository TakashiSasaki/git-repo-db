# ADR 0036: Ref observations, immutable result claims, and shared Notes interpretation

The owner explicitly adopted the complete successor on 2026-10-29. Acceptance records the target design and does not itself establish implementation or test evidence. The replaced records are retired in this acceptance change; their exact text remains in Git history. Baseline: `ab0786cfa29e7be129c7b17517a469ec1cf8b215`, remote main checked 2026-10-29. Scope: opt-in five-responsibility Core and its integration; no ordinary Schema 21 switch. Level 3 Full ADR is appropriate: this changes authority, durable identity, evidence, interchange and backup.

Rule labels: **A** owner-accepted; **I** inherited accepted contract; **P** engineering proposal for review; **U** unresolved policy. A P is not an existing owner decision. A U must be resolved or supported scope explicitly bounded before the relevant admission path is implemented.

## Decision

### D1. Individual observation and identity

**A.** A `RefObservation` is one genuine observation of one exact ref in an immutable subject: permanent repository UUID, lossless full ref name, original source attribution and actual observation/visibility scope sufficient to identify what was read. These are independent of the result; a same-key contradictory subject is identity misuse and must not overwrite. Store source descriptors as self-contained non-secret evidence, not mandatory Context/Access FKs. Preserve actual observation time if available, separately from receipt time. A single ref read can stand alone without an enumeration.

**I.** Independent immutable physical CAS copies and evidence-derived eligible candidate selection remain distinct from observation identity. Admission requires no issuer registry. Exact clone-origin reassignment, locking and transaction mechanics remain engineering work. Source associations remain known-positive; absent metadata is not itself corruption. Git-only acquisition may issue observations without a registered remote Provider.

**A.** `RefObservationKey` is exactly `(observation_origin_uuidv4, ref_observation_uuidv7)`, direct portable domain identity and dependent reference, not a storage surrogate. Validate version, variant, canonical value and full equality. Origin is the stable actual issuer, not repository, Provider, Context Source or Access scope. A genuinely new read gets a fresh v7, including a reread during an old acquisition request; the same pinned result replayed, reimported, forwarded or reanalysed retains both components. Independent issuers, cloning and collision handling must avoid misattribution; duplicate/reused inconsistent keys cannot overwrite. Origin is an unauthenticated attribution, not a signature. UUIDv7 embedded time/order, arrival, root ordering and decoder are not observation time, freshness, truth or priority.

**A/P.** Concept/type and table/field names: `RefObservation`/`ref_observations`, `RefObservationClaim`/`ref_observation_claims`, `RefEnumerationObservation`/`ref_enumeration_observations`, `NotesMapping`/`notes_mappings`, `NotesMappingClaim`/`notes_mapping_claims`, `NotesMappingGroup`/`notes_mapping_groups`, `NotesMappingEvidence`/`notes_mapping_evidence`, `NotesRoleEvidence`/`notes_role_evidence`. These are semantic names, not a prescribed table count. Rename only individual `Capture` to `RefObservation`, its pair to the names above, `capture` attributes to `ref_observation`, and Coverage owner kind `capture` to `ref_observation`. `Capture.key` currently includes other coordinates and is not the new pair. Do not rename unrelated acquisition IDs, `git_observations`, or make generic `Provenance.observation` a required FK.

### D2. Immutable results and comparison

**A.** A `RefObservationClaim` is an immutable, attributed original result statement about K. `presence_state`, `ref_form`, `direct_target_object_oid`, `symbolic_target_ref_name`, `resolved_target_object_oid`, `peeled_target_object_oid`, and `root_object_oid` represent their actual distinct meanings; object identities include `(object_format, object_oid)` and may be unknown. No symbolic or peeled value is invented when the adapter did not read it. A known present ref with unknown target, an explicitly confirmed absent ref, an acquisition failure/unknown, and an unobserved ref are distinguishable. Failure progress belongs in Operational; unobserved can be absence of a record; no requirement for five stored enum values or a failure ledger.

**A/I.** Exact replay means equality of full semantic subject, result, actual scope and original report/evidence coordinates, not equality of K alone, a digest, sender label, or arrival route. A genuine later report about the same original observation may append a known R after an unknown-target report. Keep original report and coordinates unchanged; adding R never updates or rebinds it. A fresh read is a new K even if it yields R. If an identical immutable evidence coordinate is reused for a different value or subject, reject it as incompatible replay without changing existing facts. Genuine distinct reports are not collapsed solely because values agree.

**A.** The owner selected option B: genuinely distinct attributable original reports under K that assert incompatible known targets R and S are retained as separate immutable Claims, with an explicit derived conflict. Never silently choose a winner or rebind existing evidence. Exact duplicate replay is idempotent, and reusing an existing immutable evidence coordinate for a different value or subject is rejected. Compare claims only within the same actual subject and comparable source/visibility/time/evidence scope; incomparability is not itself conflict or proof of current state. The owner also selected retention and explicit conflict for separately attributable present and confirmed-absent claims about the same K and immutable subject when their scopes are comparable. A failed acquisition is not confirmed absence; a changed immutable subject is rejected and an actual new observation has a new K.

### D3. Enumeration and scoped absence

**P.** `RefEnumerationObservation` denotes one original scan/explicit enumeration event with its own genuine portable identity and immutable original source attribution, repository, requested `enumeration_scope`, visibility, actual `enumeration_state`, completion/terminal evidence, bounds and observation time when available. Its identity protocol must be a real event identity, not a storage-only surrogate; the exact encoding and allocation are I2 engineering work. It is not a database read snapshot and does not itself assert a remote atomic snapshot. A discovery operation involving two scans has two separately identified enumeration events; an optional operation association may state their relationship but cannot replace, merge or extend either event's evidence. Re-delivery of the same event preserves its identity and full evidence.

**P/A.** Explicit typed membership/derivation links identify the precise enumeration event and its actual individual `RefObservationKey` / `RefObservationClaim` produced by that event, including a specific nominated-ref absence claim where supported. Standalone ref observations have no mandatory enumeration parent. The link records whether the observation came from an actual item or a specific negative lookup/conclusion; it does not infer that all names outside returned members are absent.

**A/I.** Confirmed absence requires an actual named ref and a successful lookup or a completed enumeration whose documented visibility and scope cover that name, with source and concrete completion evidence and no adapter or access failure invalidating the conclusion. It means absent in that particular source/visibility/observation scope, not deleted globally or absent on a remote that was not queried. Partial/failed scans, inability to resolve a target, missing evidence and no observation cannot establish absence. Do not enumerate an unbounded ref namespace into negative rows. Repeated agreeing local scans do not prove atomicity or remote absence; preserve each scan's genuine boundaries. Historical presence and absence remain append-only.

### D4. Mapping, original statements, and receiver evidence

**A/P.** `NotesMapping` represents shareable structural relationship content keyed by the actual typed root, interpretation kind/version and interpretation scope plus all semantic mapping coordinates, including `annotated_object_oid`, `note_object_oid`, and exact `mapping_path` as relevant. Equality is full semantic equality under the same grammar/scope; equal roots alone are insufficient. Origin-specific statements remain `NotesMappingClaim` and immutable coherent `NotesMappingGroup` with actual observation-result claim, provenance, scope, complete/partial/unknown status, full ordered or unordered membership as applicable, and value. Sharing content does not merge K1/K2, erase original reports or imply verification.

**I/P.** `NotesMappingEvidence` records each genuinely distinct decoder/analysis/verification with `decoder_name`, `decoder_version`, `interpretation_kind`, `interpretation_version`, `interpretation_scope`, `verification_scope`, originating evidence and its concrete source claim/root. Exact replay is idempotent; D1 and D2 independent checks remain distinct if their evidence coordinates differ even if output agrees. A claimed sender verification is an attributed report, not receiver verification. Full semantic keys use actual domain coordinates, not an authority-changing digest or receiver row surrogate. Atomic group visibility and immutability remain; two partial groups do not constitute a complete group without a separately supported complete-scope claim. Preserve ADR 0020's genuine independently attributed competing *Notes member* reports and derived conflict; apply owner-selected B to distinct known-target reports as specified in D2; the same policy applies to comparable present/confirmed-absent claims under the same K and immutable subject.

### D5. Root-specific role proof and retained body

**I/A.** `NotesRoleEvidence` links the exact immutable ref result claim to its concrete typed root, relevant locally checked structure/interpretation, target, path, and note OID. A body admission binds that same role proof and exact independently checked Git blob type, length, OID and physical digest to retained bytes. A later claim cannot redirect existing proof or body permission from R to S. Reject body retention on sender `verified` alone, mapping existence alone, or correct body hash alone. A direct tree root needs no invented commit; a commit root needs the actually relevant commit-to-tree connection. A sufficient locally verified partial path proves only that path, not a complete inventory; do not require target file body, or allow retention authority to propagate to that body. No ordinary file-body archive; preserve metadata-only and zero-body operation. Bounded proof encoding and grammar remain engineering work within ADR 0022's threshold and unfinished B03 scope.

### D6. Exchange, Query, Coverage, backup and failure

**P/I.** Selective Exchange must explicitly select by an individual ref observation key and/or an actually supported repository/ref scope, including absence and unknown-target claims without a fake OID. Object-root selection includes only observations actually linked to selected roots; it cannot discover rootless observations from an OID. Selection states which route was used and does not invent closure. Expand required immutable subject, exact claim, enumeration links when selected, mapping/evidence/role dependencies and original attribution; never expand retained bytes unless allowed and requested. A receiver validates semantic equality, dependencies and applicable structure locally before body admission. Reverse/repeated/onward transfer preserves identities and reports without trusting sender verification. Define bounded wire fields, limits and errors in I3; no need for Context or fake object/body rows for Core metadata.

**I.** Preserve Query `auto` and explicit `core_only` behavior, coexisting Context validation even with Exchange `include_context=False`, and Operational prerequisites for Core-only receive; do not infer these boundaries from the selection flags. Coverage retains five claim columns, typed owner, latest observation candidate set, equal/incomparable conflict and stale behavior; no old complete fallback. Git-only and paired backup/manifests preserve all new authoritative data and honest scope, typed identities, exact retained bytes/checks and pairing. Access remains separately backed up; Operational/Search are reconstructible and their loss cannot invalidate Core or reset a continuing request's cumulative budget.

**I.** Unauthenticated external reports retain their original issuer/source attribution and its qualification; no certificate, key enrollment, signature or issuer registry is required. Preserve acquired signature-bearing Git bytes without asserting authenticity. A report or replay comparison does not establish issuer, remote ref, time or actual bytes. Salvage candidates require typed revalidation, preserve uncertainty, do not execute recovered schema or import success flags, and lack of a signature alone is not a rejection reason. Invalid incoming reports alone do not prove catalog corruption. Actual selected/emitted allowed bytes are checked and immutable physical copies remain separate.

**I.** All Core authority is INSERT-only including technical records; no UPDATE/DELETE/REPLACE, in-place repair, hidden publication or generic success ledger. Finite configurable limits charge actual work cumulatively across the same explicit request's continuations/retries, including re-reads and verification; no fake closure or silent truncation. If authoritative corruption is detected, stop ordinary catalog operation, preserve suspect source read-only, salvage as untrusted, restore verified backup into a fresh destination and merge only revalidated data per ADR 0038 (the accepted successor to retired 0026). SHA-256 detects corruption, not source authenticity. Positive-or-NULL observed/acquisition times, positive required Coverage times and signed native Git times follow ADR 0028.

## Constraints / Do NOT

- Do not use a UUID timestamp as observation time or ordering, equate issuing origin with source/repository/access scope, overwrite or mutate any original subject/claim/evidence/group, or mistake replay for a fresh read.
- Do not call a ref absent from a failed or partial scope, or translate two local scans into a remote atomic snapshot. Do not produce unlimited negative rows.
- Do not claim that shared content, sender flags, UUID equality, notes relation or a verified note's own bytes establish local structural proof or permission to archive target/file bodies.
- Do not infer a complete group by combining partial groups, invent unobserved ref resolution, force a fake root, Context or Access row, or turn operational failures into a generic Core success/failure ledger.
- Do not widen trust, automatically migrate real catalogs, use storage-only IDs or hashes as authoritative semantic keys, or activate normal Schema 21 as part of this design.

## Context & Reason

Current opt-in `captures` has the UUIDv4 pair plus mandatory root and `note_roles`/retained notes bind that concrete root; this correctly prevents accidental proof reuse but cannot represent scoped absent or target-unknown refs as captures. Ordinary acquisition emits a snapshot, while Notes discovery pins per-ref captures and a separate snapshot that does not directly link member keys. The Notes adapter explicitly describes two local scans as non-atomic and not proof of remote absence. The native adapter does not currently retrieve symbolic target names. See fixed sources in References and the source-oriented boundary map.

Root-based deduplication loses the fact of two observations; root-owned mutable observations conflate unknown-to-known supplement with rewriting evidence. Individual immutable identity + immutable report claims preserves both. Shared interpretation content saves redundant structure without reassigning provenance or proof. The cost is longer semantic keys, explicit evidence coordinates and link validation, richer selective Exchange and durable retry design. Known-target conflict policy is owner-selected option B; comparable present/confirmed-absent claims under the same K and subject also remain as explicit conflict.

This ADR makes a substantive whole-record replacement of ADRs 0018, 0019, 0020, 0021 and 0027: the old UUIDv4 observation key and unconditional rejection of a different known root under the same observation conflict with the accepted UUIDv7 identity and option B. The clause map identifies the changed rules and surviving successors, including the independent trust, salvage and verification norms of 0027. ADR 0016 permits a typed conflict and its occurrence/attribution rules survive; its delegated identity terminology and active references require synchronization. The successor map below identifies preserved and changed clauses; the detailed reviewed map remains available as supporting documentation. No historical execution record is rewritten.

## Consequences

After independent review of the accepted documentation change, I1 defines types, admission, DDL, constraints and Coverage; I2 implements actual reads, enumeration, pinning and proof; I3 integrates Exchange, Query and backup; independent validation must inspect the actual stack head. Physical layout, indexes, encoding, transactions and tests are engineering proposals. Existing catalog compatibility, migration, deployment, merge and release are not implied. Examples in companion file are requirements, not executed tests. The repository's exact current implementation and validation status remain separate from this proposal.
