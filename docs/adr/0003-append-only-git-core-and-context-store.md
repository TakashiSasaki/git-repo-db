# ADR 0003: Append-only Git Core and durable Context Store

- **Status:** Accepted target architecture; **not implemented** at the decision baseline. Metadata-only admission is narrowly superseded by [ADR 0004](0004-metadata-only-git-core.md).
- **Decision date:** 2026-10-14.
- **Owner decision:** Separate Git-intrinsic permanent facts from repository-associated PR, Issue, review, comment, Provider and Source context. Git Core is strictly append-only; Context is an independently durable, mutable-authoritative store.
- **Decision baseline:** `main` at `b329efacafe612404848dfd26424eec219680e4c` (implemented Core Schema 21 / Operational Schema 1 / Search Schema 1, 70 + 10 + 4 product tables).
- **Predecessors:** [ADR 0002](0002-three-store-boundary-architecture.md), [ADR 0001](0001-validation-lifecycle-architecture.md), [No independent Publication](../phase2/no-independent-publication-adr.md).
- **Implementation preparation:** [Git Core / Context transition plan](../architecture/git-core-context-transition-plan.md).

**Later owner decision, GCTX-M01:** [ADR 0004](0004-metadata-only-git-core.md) requires Git Core alone to catalog commit/parent/tree/blob attributes and relationships with no raw object bytes. It overrides verified-only metadata admission, not append-only storage, Context independence or exact checks on optional byte-verified representations. Verifier domain responsibility was later fixed by [ADR 0008 / GCTX-M05](0008-domain-split-git-verification-ownership.md): Core owns Git intrinsic verification and necessary durable evidence; Context owns Provider assessments; Operational owns Jobs. Exact evidence/health schema remains open. Read the scoped supersession before applying earlier verified-byte wording below or in historical handoffs.

## Motivation and conceptual boundary

A local-only Git repository is a complete subject for the catalog even when there is no GitHub account, API, pull request, issue, comment, review, or hosting Provider. A verified Git object and the fact that a repository/ref was observed at a particular acquisition do not cease to be facts when a branch is force-pushed, a hosting service is removed, or a PR is edited.

The former "Core" grouped all durable domain information, including mutable latest-state Provider records. Its append-only restrictions were consequently heterogeneous: Git objects and captures were permanent while `issue_resources`, `review_resources` and `document_state` updated in place and left previously interned `text_bodies` unreferenced. Moving *only the mutable pointer* out of that Core would not solve the content-retention problem. The associated Provider text belongs with its Provider domain in Context, not in an otherwise Git-only immutable byte store.

**The partition key is what the fact describes, not whether an individual row happens to be immutable.** An immutable PR observation is still Context. A historical ref observation is a Git fact even though the *current* value of the ref can change.

This ADR changes the accepted **target architecture**. The checked-out three-store DDL and running program remain the **implemented baseline** until separate implementation PRs land. Do not label today's `catalog.sqlite3` as already strictly append-only.

## Binding target store boundaries

| Store | Authoritative responsibility | Persistence and mutation policy |
| --- | --- | --- |
| **Git Core** (new immutable Git domain store) | Stable repository identity; attributed Git metadata/relationships under ADR 0004; optional verified Git object bytes and intrinsic DAG; actual Git acquisitions, ref/root/snapshot observations, verified provenance, and required immutable Git integrity evidence | **Application-level INSERT-only**. No UPDATE, DELETE, REPLACE, destructive correction, mutable progress flag, or automatic/manual content GC of admitted Git facts |
| **Context** (new durable associated-information store) | GitHub/Provider services, PR/MR, Issues, comments, reviews, threads, Source inventory and memberships, contextual scopes/evidence/conflicts, PR-to-Git relationships, associated UTF-8 bodies, and associated Exchange intake | Authoritative and **not disposable**. Current-value tables may UPDATE according to existing latest-state/conflict rules. Other Context facts may be immutable. Future explicit text GC is separately governed |
| **Operational** (retained) | Jobs, attempts, leases, reservations, retry/checkpoint execution bookkeeping and cache locators | Transient/reconstructible execution state; keep PF-P04, PF-P07, PF-P11–PF-P13 guarantees in applicable scope |
| **Search** (retained) | FTS5 and other rebuildable derivatives of Git Core and/or Context | Explicitly created/rebuilt; not a source of domain truth |

The target has **four logical/physical SQLite stores per full-featured catalog**, rather than the former three. Git-only use **must work without initializing or having a Context database**; absence of Context may only make Context-specific features unavailable, never render valid Git Core contents unusable. A Context used to hold authoritative Provider data must never be silently discarded or regenerated as if it were Operational/Search. Exact filenames, schema versions, and table totals will be selected and verified in implementation PRs; the existing `catalog.sqlite3` name and "Core Schema 21" are **not** target claims.

### Git Core facts and append-only meaning

1. **As narrowed by ADR 0004:** Git metadata identities/attributes/relationships may be accepted without raw bytes or prior OID rehashing, with truthful provenance and qualification. A representation claimed as byte-verified must still pass the required byte/type/size/identity checks, and its intrinsic structure must be installed atomically. An unavailable child is represented by its actual OID and unresolved relationship, **never a fabricated verified object**. Metadata admission is not forced to await that byte-verified representation.
2. Preserve what was **actually obtained or observed**, including acquisition identity, repository identity, origin and observation time/scope; do not fabricate a remote observation by reconstructing from present refs. Each observed ref target is a separate immutable observation. A later force-push/ref deletion does **not** overwrite or revoke an earlier observation or delete earlier objects.
3. An object need not remain reachable from *today's* refs to remain historical Git evidence. Once admitted, Git facts and required physical Git bytes are retained; Git-only Core has **no automatic or manual content reclamation** under this ADR. ADR 0004 permits nonacquisition, not deletion of previously retained bytes.
4. SQLite's physical pages, indices, journals and WAL may be rewritten by the engine. "Append-only" here strictly means **no application-visible UPDATE/DELETE of rows representing Git Core facts, including in-Core technical revision/progress rows**. Reject `INSERT OR REPLACE`, `ON CONFLICT DO UPDATE`, drop-and-recreate, schema-side mutable loopholes, and hidden provider-derived version tables. Validate same-identity re-ingestion against the existing content; identical re-ingestion is idempotent, differing content is an integrity/conflict error. Under ADR 0004, distinct attributed assertions about the same nominal OID must not be mistaken for the same assertion identity or block later correct bytes.
5. Previously mutable fields such as `snapshots.complete`, `acquisition_roots.complete`, `git_objects.verified`, late-filled object-ID pointers, CAS integrity/repair status, `preservation_obligations` progress, and `database_identity.local_revision` **must be audited and remodeled**. Use additional immutable fact/completion records, derived read views or legitimate Operational progress as appropriate. Do not simply permit an UPDATE on Git Core to preserve an incumbent implementation.
6. Explicit decoder provenance and independently checked Git interpretations may be immutable Git-derived facts, but no new "winning decoder", generalized history or ref-current policy is authorized. ADR 0004 additionally permits qualified supplied metadata; do not call it verified-byte decoding without evidence. Quarantine, corrupt-byte diagnosis and repair must preserve their established guarantees, including CAS-41; **in-place repair of admitted Git Core bytes conflicts with this ADR**. Define append-only-safe recovery (or restore from verified backups) before shipping. No ability to edit Git Core is granted for exceptional repair.
7. Repository `repository_uuidv4` permanence is preserved. A minimal repository registration and actual Git capture provenance must stand without `service_instances`, `sources`, PRs or URLs registered in Context. Human names, preferred endpoints, aliases, Provider bindings and temporary acquisition configurations are not automatically immutable Git facts. Required minimal provenance for ADR 0004 metadata likewise cannot depend on Context.

### Context facts and dependency direction

1. PR/MR, Issue/comment, review/thread, Source/Provider metadata, current document text and their required completeness/evidence remain **Context**, even when a given event or associated record is immutable. Preserve Q01-B/Q02-B/Q03-B, known-positive Source semantics, real field-specific clocks, missing-versus-null, conflict alternatives, required children, actual code head/base/role anchors, and the prohibition on hidden full API edit-history snapshots. Unverified status alone does not turn modeled Git attributes/relations into Context data under ADR 0004.
2. A PR-to-commit/head/base association or PR-initiated Git acquisition belongs to Context **as an association**. The real Git object or capture can be admitted to Git Core without the PR. Context may reference Git Core using stable portable identities/OIDs; **Git Core facts may not require a Context row to be valid or readable**.
3. A single old table may need **splitting**, not wholesale relocation: `root_origins` contains both Git ref origins and PR/code assessment origins; `git_acquisitions` references `source_id`/`repository_endpoint_id` and carries PR purpose; Git closure/Code assessments and coverage mix subjects. Audit domain ownership before deciding the final schema. Do not move a Git fact into Context merely because a PR caused its collection.
4. Place Provider-domain shared `text_bodies` with Context and manage its lifetime there. Do not leave PR text orphaned in Git Core or treat mutable current state as a permanent Git observation. Context text remains exact UTF-8/sha256-addressed with collision checks and current preserved evidence; its future manual-GC policy is separate.
5. Keep the existing removal of independent Publication. No universal bundle/seal/eligibility owner, generic event log of all PR edits, parser-version winner, or cross-store publication gate may be introduced to facilitate the split.

### Isolation, transactions and recovery

- **Git-only path:** Core initialization, real local-Git acquisition, object/observation query, verified export and backup must have no hard dependency on Context, GitHub credentials or network access. ADR 0004 also requires metadata-only import/query/traversal/Exchange/backup without raw payloads; verified raw export remains a separate byte-dependent operation.
- **Cross-store references:** SQLite foreign keys do not cross attached database files. Where Context refers to Git Core, validate typed portable identities and the evidence appropriate to the claimed relationship at the application boundary. Under ADR 0004 a metadata association need not imply a byte-verified object; missing dependencies must never be silently treated as verified closure.
- **Cross-store writes:** A Core fact must remain valid if later Context bookkeeping fails; reprocessing must be idempotent and not forge an earlier observation. A Context association must not falsely claim available Git closure if the Core write did not commit. Design the ordering, fences, failure reconciliation and actual atomicity policy in a downstream design/implementation PR; do **not** silently extend PF-P07's *Core/Operational* relaxed atomicity rule to two authoritative stores.
- **Snapshot/read semantics:** A Git-only query reads one coherent Core snapshot. A combined Git+Context query needs a documented consistent version/fence protocol and conservative handling of absent, stale or conflicting dependencies; it must not mix versions and claim verified coverage.
- **Retention:** An unreachable-from-current-refs Git object stays in Core. Context retaining only latest Provider state remains allowed. A PR deletion, Provider roster absence, contextual GC or transport archive expiry must never cascade to Git facts. Backend limitations do not permit fabricated evidence.
- **Backup/restore:** A Git-only backup can cover Git Core alone and must be identified as *Git-only*. A **full catalog backup preserving Context data must include both authoritative stores** (plus required manifests/integrity metadata) as a mutually consistent set; Operational/Search are excluded. Validate per-store identity/format/hash, the pairing and referential fences before promoting a restored pair. An unmatched/missing Context file must not be reported as a full-catalog restore. Retain CAS-41 quarantine accounting and atomic no-overwrite publication guarantees. The exact multi-database snapshot and restore protocol remains an implementation design task, not permission to assume two independent file copies constitute one consistent snapshot. A complete ADR 0004 metadata-catalog backup does not claim complete raw Git repository restorability.
- **Search:** Search is a derivative of the requested source domain(s). Git-only searches use Git Core; Context queries use Context, with Git joins only when resolvable. Missing/stale Search falls back to a truthful direct scan of the **appropriate authoritative store(s)** with diagnostic notice, never to a Core-only scan falsely claiming PR/Issue completeness. PF-P16/PF-P17 explicit rebuild/creation remain. Under ADR 0004 normal metadata search must not depend on raw-object availability or implicit fetches.
- **Operational:** Execution leases/cache remain disposable without affecting either authoritative store. It may be recreated where PF-P12 permits; Context may not. Retained Git physical cache GC does not delete accepted Core bytes.

## Precise changes to prior decisions

[ADR 0002](0002-three-store-boundary-architecture.md) remains an authoritative historical accepted decision and implementation reference. **This ADR explicitly supersedes only incompatible target claims:**

| Former decision | New target interpretation |
| --- | --- |
| **PF-P06**: Core+Operational(+Search) placement, with all durable domains in one Core | Replace its physical placement with **Git Core + durable Context + Operational + Search**. Retain separation of durable truth from disposable execution/search |
| **PF-P08**: normal backup copies Core only | Replace for **full-catalog** backup: include Git Core **and** Context. Git-only backup remains permitted and must be labeled as such. Operational/Search remain excluded |
| **PF-P05**: no present domain-text GC, future explicit manual GC | Preserve "no currently implemented domain-text GC"; move Provider text into Context. Previously discussed GC-01/GC-02 conservative dependency analysis and execution-time recheck apply to **future Context text GC**, not Git Core. The conditional GC-03 deletion-authorization mechanism is **not fixed** for the redesigned Context, and GC-04 atomic/batching choice is open |
| **PF-P14/PF-P15**: Search derived from old Core; direct Core scan fallback | Retain rebuildability and diagnostic fallback, but use the **correct authoritative source** for each query (Git Core and/or Context) |
| **PF-P07**: no atomicity guarantee for Core versus Operational | Retain for disposable Operational; **does not settle** the authoritative Git Core/Context transaction and backup pairing |

**Not reopened:** repository UUIDv4 permanence, Q01–Q04, no Publication, typed identity and exact provenance, Coverage five-column semantics and partial/unknown behavior, Git canonical verification when claimed (metadata admission is extended by ADR 0004), true ref/capture facts, sender-trust limits, Unix epoch `_us` time, existing verified CAS integrity/CAS-41 guarantees, PF-P01–PF-P04/PF-P09–PF-P13/PF-P16–PF-P17 where compatible, ADR 0001 development/release testing boundaries. Source/Provider current data still requires durable preservation; "peripheral" never means "discardable."

## What this design PR does **not** decide or implement

- No production DDL, schema version, database file rename, migration, runtime operation, manual GC command, data deletion or PR merge in this design-only change.
- Do not infer an exact four-store table count from the old 70/10/4 count; moving/splitting tables changes counts and FKs.
- Exact names/formats of files, cross-store transaction and recovery protocol, append-only replacement for each mutable Git Core column, physical CAS repair mechanism, backup pairing algorithm, detailed Exchange wire evolution, and full table-by-table allocation are **implementation design work** constrained by the binding boundaries above. Document scoped decisions in their own PR before coding if they require owner choice. ADR 0004 adds mandatory metadata-only capability but does not select its schema, conflict-read policy or verification placement.
- Existing DS-R01 evidence reclamation, DS-R03 decoder-selection extensions, DS-R04 enhanced Exchange trust, DS-R05 unresolved cross-repository ownership exchange, DS-R06 optional archive retention, DS-R07 broader deletion propagation and DS-R08 CAS-76/CAS-77 source research remain deferred/unchanged.

## Required implementation evidence and acceptance criteria

Use the [transition plan](../architecture/git-core-context-transition-plan.md) and ADR 0004's additional metadata-only counterexamples. Before claiming completion, independent reviewers must verify:

1. A new Git-only catalog works with **no Context DB**; genuine local-Git capture and queries round-trip through backup/restore. It must also operate on supplied commit/parent/tree/blob metadata with zero raw payloads under ADR 0004.
2. SQLite and application tests prove **no UPDATE, DELETE or REPLACE of Git Core facts** (including recovery paths, staged intake, future hydration, late Git dependency resolution and administrative operations). Force-push/reobserved-ref counterexamples retain both observations and the older objects.
3. PR/Issue/comment/current-value updates and Context conflict handling work without inserting those bodies or domain truths into Git Core. Missing Context data is never labeled as a successful full-catalog restore.
4. PR-induced Git acquisitions leave independent real Git evidence. Cross-store stale or missing references fail closed for guarantees requiring those dependencies, and no partial failed write fabricates a complete root, ref or contextual coverage claim. Unverified metadata is not itself a failed verified-byte acquisition.
5. Backup/restore and Exchange preserve canonical bytes where retained, SHA integrity, CAS-41, stable repository identity, provenance and verified scope; they additionally support accurately qualified metadata-only catalogs. Search rebuild/fallback and Operational loss preserve the correct authoritative-domain boundary.
6. Evidence is bound to the exact effective code/DDL tree, with focused development validation under ADR 0001, relevant independent review and explicitly invoked release qualification only when requested.

This design PR freezes the boundary; it does **not** itself certify that the incumbent Three-Store implementation has been transformed or that the acceptance criteria were executed.
