Task D — ADR 0031 I2 SQL設計の独立反例レビュー
実施日: 2026-10-21 UTC
最終判定: NOT READY（指定された現在のSQL案／段階導入設計について）

主要結論

Resources本体の三要素キー、canonical Identity、明示的識別メタデータ、
child-before-Parentの構成について、新しい阻害欠陥は確認しなかった。
しかし、I2の暫定Transferフェンスには新規のHigh欠陥F1がある。
resource_repository_relationsのendpointだけを止めても、resource_relationsの
transfer_event_reportを直接登録できる。endpointを持たないProvider-only報告は
現存のreference readerでTransferEventReportに復元される。I7 Resourceすら不要だった。
この設計のままI2段階導入を安全と承認することはできない。

これはAccepted ADRの矛盾ではなく、未対応機能を遮断する暫定実装方針の不足である。
G3=Aの再選択、I4の先行実装、Parent存在FKの復活、キーへの第四要素の追加は不要。
一般Parent報告の保存と、未実装Transfer機能の拒否を区別してフェンスを補完すればよい。

3. 確認した不変条件（試した境界での結果）

A — Identityと識別メタデータ

・resourcesはSTRICT, WITHOUT ROWID。PKはservice/kind/canonical ID TEXTの三要素のみ。
  四つの識別メタデータもgenerated projectionもPKを増やさない。
・I1aのparse_identity/encode_identityを実際に呼ぶUDFであり、歴史的cprime parserを
  差し替えて使っていない。deterministic flag 2048を実測。UDFにDB参照や外部I/Oなし。
・空文字列、空配列、[""]、[[]]、再帰配列、JSONに見えるnative文字列を区別した。
  NFC/NFD、case、空白、日本語、補助平面文字、NUL/DEL/改行を試した。
  非canonical escape、raw非ASCII、孤立／逆順surrogate、禁止型、BLOB、NULL等を拒否。
・262144 canonical ASCII bytes／4096 value nodes／32 array containersの境界を
  独自構成して最大値受理・最大値+1拒否。空配列終端と文字列終端の両depthを確認。
  local単体が上限内でも、scoped outer keyが上限を超える行は拒否する。
・Document全メタデータ省略を拒否。scoped metadataの16通りのNULLマスクを検査。
  完全globalはlocal欄=full ID、完全scopedはnamespace/subtype/native-localを再構成。
・同じ配列形状・同じ三要素キーになるGlobalとScopedの両初回宣言が成立する。
  両到着順の異なる宣言再送はINSERT/IGNORE/DO NOTHING/REPLACE/UPSERTで拒否。
  同じmetadataでのDO NOTHINGは正常に重複排除した。
・native localとserialized localの片側だけを二重encodeした不一致は拒否。
  両側を整合してnative文字列J(D)を指定すれば別の合法IDになることも確認した。
  SQLは本来のProvider契約と呼出元の誤操作を識別できないため、typed APIの役割が残る。
・review/thread/comment/documentの許容namespaceと禁止namespaceを全組合せで確認。
  予約名の不正なopaque扱い、未知名への既知metadataの付与は拒否。
  未知kindは同じ名前でもservice別に独立。大文字小文字も別キーであり、
  名前だけからProvider間同一性を推論しない。Node-ID/数値IDの正規化はadapterの責任。

B — Direct SQL

・Context全実索引のkey slots 141箇所をindex_xinfoで確認し、すべてBINARYだった。
  3/4/5/6列の参照先UNIQUEに一致するFKの成功例・wrong-coordinate・NULL拒否例を実行。
  Auxiliary FK表は比較用のみで、製品domain tableとして数えていない。
・実製品のfield_candidates/resource_relations/collections/core_referencesでも、
  正常FKと三キー各NULL・不存在referentを試した。resource CoverageのNULL逃げも拒否。
・四列Document FKのabsence markerは空文字列で、SQL NULLではない。
  wrong subtype、NULL marker、scopedをglobal markerで引用する試行を拒否。
  将来I3の引用元にもNOT NULLまたは同等の必須CHECKが必要である。
・通常UPDATE/DELETE、同一行REPLACE/UPSERT-updateは既存immutable guardsが拒否。
  不正metadata再送は競合処理前にinvalid Resource identificationで拒否する。
  複数行INSERTの後半不正行はstatement全体をabortし、前半も残らなかった。
・statement ABORTは外側transactionのprefixまでは戻さない。明示savepoint rollbackで
  unitだけを除去し、外側の合法行をCOMMIT/reopenして維持した。
・意図的defer_foreign_keys=ONの対照ではCOMMITがFK787で失敗しtransactionが残った。
  明示ROLLBACKで不正行を除去した。これを正常設定の成功には数えない。
・foreign_keys=OFFは孤児Resourceを受理し、recursive_triggers=OFFは同一REPLACEを受理。
  trusted_schema=OFFではPython UDFがunsafeとして拒否された。
  ignore_check_constraints=ONでもResource BEFORE guardは拒否したが、他表CHECKの
  無効化を安全とは評価しない。これらは非対応接続の対照であり、新規欠陥扱いしない。

4. 新規欠陥 F1（High、段階導入を阻害）

場所:
  Task C compose_proposal.py:21 — endpoint表だけのi2_transfer_stage_fence
  製品p1_context.py:799 — endpointなしのtransfer_event_reportもreaderが列挙
  製品domain/p1_context.py:1723 — Provider-only endpointを持つTransferEventReport

再現SQL: F1-reproduction.sql（実行可能な完全リテラルSQL）。
実行helper: reproduce_f1.py（候補DDLと全UDF登録後にそのSQLを実行）。

要約形（完全SQLの引数を省略した説明用）:
  INSERT INTO resources(...)
    VALUES(S,'comment',J(['issue',J('I7'),'timeline_event','event']),
           'issue',J('I7'),'timeline_event',J('event'));
  INSERT INTO resources(...) VALUES(S,'repository',J('unresolved-R'),NULL,NULL,NULL,NULL);
  INSERT INTO resource_relations VALUES(
    S,'comment',EventId,'transfer_event_report',Members,Provenance,Scope,17);

Scopeは正規のclock/event_type='transferred'/Provider ID/provided_rolesを持ち、
Membersも同じProvider ResourceKey。I7 Resource・Parent報告・endpoint行は作らない。

期待: I2がI3–I5未実装機能を全面遮断するなら、最後のINSERTをSQLで拒否し無変更。
実結果: 両版ともSQLが成功（例外なし）。report行1、I7行0、Parent報告0、endpoint行0。
既存ContextStore(db).transfer_event_reports()は1件を返し、from_stateは
unresolved_provider_only。foreign_key_checkは空、integrity_checkもokのまま。
このreference readerは実製品コードそのものだが、候補DBを手動接続して使ったもの。
製品facadeのinitialize/openや完全query経路のend-to-end成功は主張しない。

同じ不正受理をINSERT OR IGNORE、ON CONFLICT DO NOTHING、REPLACE、UPSERTでも確認。
さらにscope='{}'というmalformedな同予約名reportもSQLが受理した。
以上が6失敗で、6個の独立欠陥ではない。後者はreader側でmissing-clockエラーになり得る
入力を、I2フェンスが未実装機能として止めないことも示す。

原因: 暫定拒否はresource_repository_relationsの2 roleにのみ設置されている。
既存設計にはresource_relationsだけで表現できるProvider-only Transfer報告がある。
一般relationのrow CHECK／Resource FKは、予約名のTransfer仕様やI7報告依存を検査しない。
API拒否だけの追加ではDirect SQL経路は閉じない。

修正案（実装せず、使い捨てDBのみで対照検証）:
  CREATE TRIGGER i2_transfer_report_stage_fence
  BEFORE INSERT ON resource_relations
  WHEN NEW.relation_kind='transfer_event_report'
  BEGIN
    SELECT RAISE(ABORT,'Transfer report requires I3-I5 implementation');
  END;

既存endpoint fenceと合わせ、typed API、import、未対応readerにも段階状態を一貫させる。
general Parent/reportを一律停止したりI8を削除したりしてはならない。
新規フォーマットなので既存Transfer行のgrandfatheringも不要。
既存resource_relations UPDATE/DELETE immutable guardsは維持する。

この追加triggerで5つの報告INSERT系verbをすべて拒否し、一般vendor relationと
I8を引用する一般parent relationは受理する7件の対照を両版で確認した。
これは修正方向の証拠であり、製品への適用・修正済み判定・後段意味検査ではない。

F1は「I8 supportのnative-I7比較をI2が実装していない」という指摘ではない。
I4責任の比較を後回しにするために選んだ暫定フェンスが、報告経路を覆っていない指摘。
Accepted ADRを変更する必要はない。

次は実測した統合上の失敗／制約であり、Task Cが既に計画している作業を
別の新規欠陥として水増ししない。

・FK/indexの同時更新:
  Resources fragmentだけをコピーし既存endpoint五列FKを残す外部対照では、
  owning_repositoryのINSERTさえforeign key mismatch（SQLITE_ERROR 1）となった。
  正しいcompose_proposalは参照先をreference_document_kind/identifier_namespace_kindに
  書き換えており、その版ではFK mismatchはない。UNIQUEの広いsupersetだけでは代用不可。

・UDF登録順序:
  旧p1_schema.register_functionsだけで候補DDLを作ると
  no such function: p1_resource_identity_v1（1）。旧登録で再open後integrity_checkも
  unknown functionで失敗した。新関数をDDL作成／schema準備／CHECK検査より先に登録する。
  reference_document_kind自体はcoalesceだけのgenerated columnで、新UDFを呼ばない。
  本件を「generated expression内の新UDFの順序バグ」と誤記しない。
  新UDFはCHECK／BEFORE INSERTで必須。deterministicはSQLITE_INNOCUOUSとは異なる。

・初期化／再open／fingerprint:
  initialize/connect/expected_schemaはp1_schema中心の登録に集約される。
  外部configureだけ追加しても製品経路は更新されない。
  現行connectで候補DBを開くとcontext physical schema differs from packaged target。
  DDL、registry、fingerprint、schema manifestを同じ実装単位で更新する必要がある。
  p1_schema.verify_declaredは全storeのexpected schemaを作るので、Context UDF登録不足を
  他store初期化へ波及させないこと。SQL fingerprintだけでPython UDF本体の同一性は証明不可。

・バックアップ／recovery:
  純粋なsqlite backup()はtarget側UDF未登録でもbyte-copyできた。
  しかしそのtargetのintegrity_checkはunknown function: p1_uuid4()で失敗し、
  configure後はokになった。copy成功と意味／schema検査成功を分ける必要がある。
  p1_coordination.py:746のbackup target、recovery.py:1105以降のsource/target、
  read-only validation接続、expected_schemaを通る検査を監査した。
  ただし全paired backup/recovery製品フローを実行したとの主張はしない（I7）。

・読み出し:
  旧SELECT parent_resource_kind,...はno such column（1）。単なる列名置換だけでも不十分。
  保存済みGlobal-shaped Documentを三キーSELECT→ResourceKeyで再構成すると
  _document_contract=Noneとなりscoped decoderが成功した。保存したGlobal metadataは
  正しく残っているため、欠落はreaderがmetadataを選ばないことにある。
  metadata付きdecoder/APIをI2で実装し、semantic Parent出力をnamespaceで補充しない。
  acquisitionの階層再構成、_members/field inheritance、wire orderingを再利用する場合も同様。

・Source/Coverageと他store:
  Source positive-delete拒否、実Resource CoverageのNULL拒否、exact text hashを対照実行。
  Source/Coverage部分、Core/Operational/Search DDL、Access DDLには本案の差分がない。
  Searchの現行expected_schemaは旧登録でも成功し、Search表そのものが新UDFを必要とする
  という証拠はない。通常Search接続はp1_schema.connect経由であり、共通manifest更新と
  Contextを読むquery/rebuild/fallbackのmetadata整合が影響点になる。
  五store全機能やSource/Coverage全意味が検証済みという結論にはしない。

・I6 wire/選択/unknown preservation、I7 stored integrity/paired recovery、I8 Search。
