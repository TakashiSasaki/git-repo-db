## Independently checked product behavior

Using Python 3.12.14 with actual SQLite 3.53.1, I initialized a fresh Context DB
in a disposable temporary directory and called the production `Context`
transaction facade and actual domain types. No source normalizer, remote API,
real catalog, credentials, simplified schema or alternative SQLite binding was
used. The 14 assertion results are in [r12.json](r12.json).

The assertions confirmed:

- The same ID is distinct across service instances and resource kinds.
- Repository-parented documents, Issue-parented threads, annotation-parented
  reviews and an unenumerated `discussion` kind are rejected by real DDL.
- An independent annotation can relate to two Provider repository resources.
- A typed reported Core OID remains readable as unavailable/non-required when
  no Core object is available.
- Two Provider repositories can map to one Core UUID; forward and reverse
  queries retain both Provider identities.
- A conflicting second mapping remains a conflict; its exact replay is a
  duplicate. An unconfirmed withdrawal preserves conflict, while a supplied
  currently-qualified disposition changes the result to a single candidate.
- These mapping assertions can be stored in Context without a Core DB. This
  establishes attributed reports, **not** available Core repositories.

The qualified-evidence input in the probe was a synthetic
`MappingOperationEvidence` instance. This does not authenticate an issuer or

## R1: identity and resource-model assessment

1. **Non-Issue, informational:** service instance + kind + Provider ID is a
   usable namespace structure. Provider kind is descriptive registration, not
   a substitute for the instance UUID. Same-kind, multiple-instance isolation
   follows from the actual key. Resource IDs must already encode the genuine
   Provider namespace; UUID isolation does not fix a project-local ID collision
   within one service. Evidence: [ResourceKey](https://github.com/TakashiSasaki/git-repo-db/blob/efb55af84ccbf1183d47547d22bb6c57d8fbc8f9/src/repo_catalog/domain/p1_context.py#L639)
   and [DDL](https://github.com/TakashiSasaki/git-repo-db/blob/efb55af84ccbf1183d47547d22bb6c57d8fbc8f9/src/repo_catalog/adapters/sqlite/p1_ddl/context.sql#L2).
2. **Requirement Coverage Gap, Major:** the closed resource enumeration and
   mandatory document/review/thread parents cannot preserve all requested
   independent documents, discussions and review identities as those kinds.
   DDL rejection is correct under the current contract; calling it an
   implementation defect would be incorrect. A generic annotation with fields
   can support some annotations, but renaming every unsupported entity to
   annotation does not establish a shared typed semantic contract. Evidence:
   [resources constraints](https://github.com/TakashiSasaki/git-repo-db/blob/efb55af84ccbf1183d47547d22bb6c57d8fbc8f9/src/repo_catalog/adapters/sqlite/p1_ddl/context.sql#L26).
3. **Engineering Contract Gap, Major:** the generic key accepts arbitrary
   strings, but normalizing genuine Provider-local/composite/reusable IDs and
   authored-versus-reported metadata requires a documented adapter contract.
   The supplied production normalization is GitHub-specific; storing synthetic
   `gitlab`/`gerrit` registration rows is not end-to-end Provider support.
   Evidence: [normalization module](https://github.com/TakashiSasaki/git-repo-db/blob/efb55af84ccbf1183d47547d22bb6c57d8fbc8f9/src/repo_catalog/adapters/github/production_intake.py#L1).
   This observation alone does not prove any live Provider collision.
4. **Non-Issue, informational:** independent annotation/assessment resources,
   arbitrary typed relation names and typed reported OIDs provide substantial
   reusable infrastructure. Missing Core is not a reason to fabricate an OID
   referent or mapping. `report_core_reference` deliberately differs from
   required `link_core` dependencies. Evidence: [reference APIs](https://github.com/TakashiSasaki/git-repo-db/blob/efb55af84ccbf1183d47547d22bb6c57d8fbc8f9/src/repo_catalog/adapters/sqlite/production_context.py#L993).
   File/position schemas, actor roles and multiple-value event semantics still
   require contracts; JSON storage is not proof of those meanings.

## R2: mapping and authority assessment

1. **Non-Issue, informational:** Context placement is consistent with ADR 0029
   and ADR 0030. A Provider correspondence is attributed contextual information;
   it is neither intrinsic Git identity nor an Access execution grant.
   `repository_context` permits a Context-local FK without making Core valid
   only when a Provider row exists. Core availability must be checked
   separately from mapping evaluation.
2. **Non-Issue, informational:** immutable competing `represents_repository`
   claims and stored Dispositions preserve ambiguity and replay identity.
   Evaluation does not use newest timestamp to choose a Core UUID. A reverse
   query is a report query, not a declaration that every returned target is
   currently qualified or locally available. Evidence: [evaluation](https://github.com/TakashiSasaki/git-repo-db/blob/efb55af84ccbf1183d47547d22bb6c57d8fbc8f9/src/repo_catalog/domain/p1_context.py#L1369)
   and [typed query facade](https://github.com/TakashiSasaki/git-repo-db/blob/efb55af84ccbf1183d47547d22bb6c57d8fbc8f9/src/repo_catalog/adapters/sqlite/production_context.py#L831).
3. **Extension Opportunity, Minor:** reuse of these claims between multiple
   Context catalogs should first be considered through Exchange and explicit
   shared identity conventions. A dedicated Mapping store would add another
   authority, backup boundary and cross-file validation boundary; SQLite FK
   benefits do not extend across files. Moving claims into Core would couple
   independent Provider history to Git authority. Neither alternative has a
   demonstrated necessity in these probes. This is a recommendation to retain
   the current baseline while evaluating options, not a new architectural
   decision.
4. Six repository roles intentionally exclude a generic referenced-repository
   role. Broader annotation targets should not be silently mapped to
   `owning_repository`; Provider-to-Provider `resource_relations` and typed Core
   references already cover part of that need. Any truly new Core-Repository
   relation semantics must be presented for design judgment under ADR 0030.
