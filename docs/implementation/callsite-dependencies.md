# Implementation call-site and dependency audit

This is a source audit of implemented main `57de60b65c2ef29420a885b0c2102dc90e11fa75`, Core 21 / Operational 1 / Search 1. It does not claim four-store production support. The complete table/PK/FK/index/trigger/view inventory and disposition are in [schema-inventory.json](schema-inventory.json) and [table-disposition.md](table-disposition.md). [callsite-dependencies.json](callsite-dependencies.json) indexes every production Python module and packaged SQL fragment, source hashes, enclosing functions for literal table/view references, and all revision/fence references. Reproduce with `uv run --no-sync python scripts/audit_callsite_dependencies.py --check` (omit `--check` to regenerate after reviewing drift).

The generated index is a completeness check on source coverage and literal references, not an executed call graph. The semantic chains below were inspected in source, including dynamic SQL dispatch. A lexical match alone does not establish a writer or durable authority. Future implementation PRs must retain adversarial runtime tests for indirect paths; this audit does not prove their absence by static analysis. Prototypes remain isolated and do not change these production dependencies.

## Coverage and KEY-P01 are a joint schema gate

The binding baseline contract spells out exactly five claim columns in `docs/data-model.md:27`: `coverage_claim_id`, `coverage_scope_id`, `coverage_state`, `observed_at_us`, `details_json`. `catalog3.sql:144` makes the first a storage-only integer PK; `Store.coverage:315` generates the second as a local UUID. Neither has an accepted new-format exception. Existing semantic equality is `(actual scope, observed_at_us, coverage_state)`; details neither define equality nor break ties. `current_coverage` selects the latest timestamp *before* determining unknown/conflict; stale older success cannot fill it.

P1 must provide a five-column physical relation with directly represented semantic claim/scope coordinates, not add observation UUIDs, grandfather the integer, add a sixth provenance column, or substitute a five-column view over a six-column authoritative table. A reversible, typed, exact semantic scope coordinate can represent the existing repository/optional Provider-owner/kind tuple without a generated row ID; it must validate against its domain owner and be used directly by matching FKs. The division of that coordinate and claim coordinate between the two existing identifier-named columns is an explicit **engineering DDL task**, not a new identity policy and not implemented by this spike. Do not ship P1 without executing its exact five-column count, PK/FK, duplicate/stale/same-time alternatives, advisory-detail and Exchange reverse/repeat probes. No final target layout or new owner blocker is asserted here.

Dependent sites are `admit_claim RETURNING coverage_claim_id`, `export_current_claims`, `current_coverages`, Store scope lookup/creation, current_coverage counts/grouping, marker trigger and normalized FKs, `Graph.NATURAL/proof_requirements/_admit/export/refresh_resolution_blocks`, `pr_queries` coverage proof checks, JSON coverage details validation and CLI coverage serialization. The generated index gives each line. Changing only the PK declaration leaves these consumers incorrect.

## Mutable revision removal is a whole-interface change

The JSON `revision_dependencies` inventory contains every production line mentioning `local_revision`, `advance_local_revision`, `core_revision_fence` or `.revision()`, including direct SQL outside Store. Mutators: Store; Git parser connection wrapper and installer/reparse; importer completion/source reuse; CurrentResources transaction wrapper; identity relations; CAS diagnose/repair; GitHub persistence; collection/source/Exchange/maintenance services. Readers: CurrentResources/current API live-request compare-and-admit guards, QueryService search and cursor fences, TargetReader/TargetQueryService, Search rebuild/status/identity, Operational/Search parent catalog identity and backup/restore manifests/results. The CLI JSON schema and `scripts/schema_viz.py` also expose old identity/revision fields (the latter is documentation generation, not production authority).

P1/P2 must replace revision with a pinned immutable Core evidence boundary; Context can have its own mutable state token in Context. P6/P7 consume a pair of scoped boundaries plus physical instance/pair identity, and use a supported read/write barrier when a coherent cross-store result is requested. A derivative generation can record the relevant pair but cannot authorize data. Never keep incrementing Core revision, infer freshness solely from `MAX(rowid)`, or introduce an authoritative global publication/event ledger. The crash prototype supplies experiment evidence, not a drop-in production fence.

## Views, triggers, indexes and generated contracts

All named objects are serialized in `schema-inventory.json`; SQL-fragment references are in the dependency index. `valid_git_*`, `available_git_objects/acquisitions`, `valid_ref_captures`, `available_snapshots/current_snapshots` currently impose byte/verification/whole-closure conditions. Replace their metadata-read semantics, retaining exact byte checks only for claimed checked scope. Hydration/verified/complete UPDATE guards are intentionally looser than target INSERT-only. Core `coverage/current` views and current-state `eligible_*` views read conflict staging: moving those records changes domain eligibility and cannot be treated as cache cleanup. Recursive identity-equivalence views straddle repository/Provider meaning. Root-origin and acquisition closure triggers, decoder/content/UDF guards, generated JSON nested-reference checks and PK/FK indexes must be regenerated against the new semantic schema as a unit.

`schema.py` hashes composed resource bytes; Store and TargetReader compare stored fingerprints, while Operational/Search verify their independent identities/fingerprints. `json_contracts.guard_sql()` produces `resources/json_contracts.sql`; generated equality is checked by `scripts/audit_publication_free.py:216`, `scripts/validate_remaining_contracts.py:379`, JSON integration tests and installed distribution tests. Earlier audit scripts pin retired formats/Publication-free assertions and need explicit disposition in P1/P8; do not silently rewrite historical receipts. `scripts/schema_viz.py` includes soft cross-store instance/revision edges and must change with final ownership. FTS tables are dynamically created in `index.rebuild` and have SQLite-owned shadow tables beyond the four product Search tables; P6 must audit those too. Their physical existence never makes them authoritative or permits excluded text.

## Engineering work versus owner decisions

Established: four stores, INSERT-only Core, metadata-only operation, full typed OID, permanent repository UUID, direct Capture pair, attributed immutable alternatives, no ordinary-file archive, exact notes proof/body verification, finite cumulative actual-work budgets, five-column latest Coverage, known-positive Sources and no Publication authority. All accepted scoped supersessions apply; legacy behavior described here is not policy permission.

Engineering: exact semantic DDL/FKs and five-column encoding; proof encoding/grammar, finite numeric budgets and counters; Source/config split; cross-store crash/read/backup fences; typed Exchange and reconstruction; immediate corruption stop and fresh activation. These need implementation and tests, not new owner questions. Zero concrete architectural contradictions were established by this call-site audit. Unexecuted target production tests and full-release acceptance are remaining implementation verification, not completed claims.
