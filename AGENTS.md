# Coding agent guide

This guide applies repository-wide. Task specifications and agent handoffs are written in English; user-facing explanations may be Japanese.

## Product and authorization

**Latest accepted append-only physical CAS recovery: [ADR 0012 / GCTX-M08](docs/adr/0012-append-only-multiple-cas-physical-instances.md).** Distinguish nominal Git OID, logical CAS payload `(representation,sha256)` and separate immutable physical-instance identity. Keep damaged instance I1 and its durable physical diagnosis; recovery appends independently byte/OID-validated replacement I2 and narrowly typed association/evidence without UPDATE/DELETE/REPLACE of old Core bytes or trigger bypass. Logical payload availability via I2 does not erase I1's physical fault, lower CAS-41 active physical quarantine count automatically, or authorize Git Core GC. Intra-SQLite copies are not independent disk fault domains. GCTX-M09 will decide candidate selection, exact active-quarantine projection and any lawful physical-instance retirement; no time-based winner, implicit health or generic Publication.

**Latest accepted physical-integrity assurance: [ADR 0010 / GCTX-M07](docs/adr/0010-operation-scoped-cas-physical-integrity.md).** Apply operation-specific guarantees: metadata-only and historical canonical queries need no per-read raw-body rehash, but successful verified raw-byte export and requests for current physical integrity MUST validate the actual selected/emitted bytes with consistent instance/snapshot scope; old admission or last scan cannot certify healthy-now. Known faults/quarantine fail closed for byte-dependent operations; explicit audits report as-of scope. Never emit unverified bytes as a successful verified output or verify A then output unprotected B. Keep Core append-only, no generic scan-success history, CAS-41 active physical quarantine accounting. GCTX-M08 immutable alternate-instance recovery is fixed by ADR 0012; GCTX-M09 candidate selection/quarantine and exact output/snapshot implementation remain undecided.

**Latest accepted byte-admission evidence: [ADR 0009 / GCTX-M06](docs/adr/0009-bounded-byte-admission-and-physical-health.md).** When optional real Git bytes are admitted, Core atomically binds locally verified format/OID/type/size, CAS raw bytes and checked intrinsic structure as a bounded immutable representation fact. That is historical admission evidence, not current physical integrity. Metadata-only Core requires no bytes or proof. Do not create a per-scan success ledger, mutable `git_objects.verified`, fake CAS payload or generic Publication. Physical faults require durable Core diagnosis and CAS-41; GCTX-M07 operation-scoped assurance is fixed by ADR 0010; precise snapshot/streaming protocol, GCTX-M08 recovery via additional immutable physical instance is fixed by ADR 0012; GCTX-M09 selection/quarantine and exact physical DDL remain open.

**Latest accepted verifier responsibility: [ADR 0008 / GCTX-M05](docs/adr/0008-domain-split-git-verification-ownership.md).** Git-intrinsic OID/type/size/byte checks, intrinsic structures, own-claim conformance and necessary immutable evidence belong to Git Core; Provider-specific assessments to Context; disposable verification Jobs/retries to Operational; Search is derivative. A shared library does not make Context authoritative for Core admission. Intentional metadata-only absence is not corruption. Historical byte admission, field-specific correctness, current physical health and graph closure are distinct. GCTX-M06 fixes bounded immutable historical admission proof by ADR 0009; GCTX-M07 assurance tiers are fixed by ADR 0010; exact snapshot/locking protocol remains open. Do not create a generic verification success ledger or launder sender claims.

**Latest accepted ordinary Git metadata read policy: [ADR 0007 / GCTX-M04](docs/adr/0007-verification-aware-git-metadata-reads.md).** Prefer only receiver-verified byte-derived canonical values for precisely checked fields/relations; without byte-backed evidence, agreed reports remain explicitly unverified and contradictory reports surface as conflicts/alternatives. Never infer complete parent/tree sets from a union, select winners by source/time/decoder, or silently promote assertions merely because their OID has been verified. Raw byte identity, per-field interpretation, current physical availability and graph closure are separate. This is a derived read policy, not a Core mutation; verifier domain responsibility is fixed by ADR 0008 while evidence record layout remains open.

**Latest accepted recording granularity: [ADR 0006 / GCTX-M03](docs/adr/0006-field-claims-and-observation-scoped-relations.md).** Store logically scalar Git attributes as individually attributed field claims, and ordered parent/tree relationships as typed, observation-scoped groups with genuine ordering/scope evidence. Never merge unrelated groups into a fictitious complete list, infer empty from unknown, invent raw offsets or ordinals, or mutate admitted claims to hydrate them. Ordinary conflict-read policy was fixed by ADR 0007 and verifier domain responsibility by ADR 0008; physical group and exact evidence schemas remain open.

**Previously accepted identity refinement: [ADR 0005 / GCTX-M02](docs/adr/0005-common-oid-identity-with-attributed-metadata.md).** Use one logical Git Core OID identity per `(object_format, oid)` regardless of repository; source-attributed attributes/relationships and optional verified bytes remain separate. A nominal OID row is not evidence of actual object bytes, type, size, repository membership or verified closure. Core metadata statements from different observations must coexist without overwriting. Neither `git_objects` physical layout, assertion grouping, nor verification-result storage is selected.

**Mandatory owner requirement: [ADR 0004 / GCTX-M01](docs/adr/0004-metadata-only-git-core.md).** Git Core alone MUST support first-class commit/parent/tree/blob metadata and relationship cataloging without any raw Git object bytes or Context database. This narrowly supersedes ADR 0003's verified-only metadata admission, not its append-only/four-store boundaries. Never send all unverified Git metadata to Context or staging, require hidden payload fetching, or hide ordinary metadata queries behind verified-byte availability. Verification location and exact schema remain unresolved. Apply this scoped override to older handoffs, Phase 2 guidance and the invariants below; strict checks for optional byte-verified representations remain binding.

The **currently implemented** fresh format is Catalog3 Core Schema 21, Operational Schema 1, Search Schema 1 under the Three-Store Boundary ([ADR 0002](docs/adr/0002-three-store-boundary-architecture.md)). **The later accepted target**, not yet implemented, is [ADR 0003: strictly append-only Git Core + durable Context + Operational + Search](docs/adr/0003-append-only-git-core-and-context-store.md), as narrowly extended by ADR 0004 and refined by accepted ADRs 0005–0010 and 0012. Read its [implementation transition plan](docs/architecture/git-core-context-transition-plan.md) before changing domain storage, schema, Exchange, backups or GC. It implements the owner-approved [Publication-independent reconstruction](docs/phase2/publication-free-design.md), [decision](docs/phase2/no-independent-publication-adr.md) and [implementation instruction](docs/phase2/publication-free-implementation-prompt.md). See the [implementation handoff](docs/phase2/publication-free-implementation.md) and its exact-revision review/acceptance receipts. Implementation does not imply review-complete acceptance. Earlier checkpoint reports (including monolithic Schema 20) remain preserved historical evidence; their DDL fingerprints identify their exact format.

The deployed developer documentation website is accessed at https://git-repo-db.moukaeritai.work/ (published automatically via GitHub Pages from `main`).

The project is unreleased and has one developer. No old database, internal API, CLI or migration compatibility is required. Preserve Git history and other agents' uncommitted work. **Permissions come from the explicit current owner task, not from this file or an older prompt.** Create commits/branches/PRs only within that task's scope. Merge only the specifically owner-authorized PRs after required protections and validation; otherwise do not merge into `main`. An authorized merge does not authorize release, deployment, tagging, force pushes, bypassing branch protection, retained-catalog mutation, or authenticated live collection. Use disposable synthetic state; stateful CLI commands require an explicit disposable `--state-dir`. Never commit real catalogs, credentials, private content, caches or raw authenticated traffic.

## Decision authority

Apply explicit current owner decisions first, then accepted ADRs and scoped supersessions, then unsuperseded production contracts, then historical evidence. The current owner accepted Q01-B, Q02-B, Q03-B, **NO_INDEPENDENT_PUBLICATION**, binding **PF-P01–PF-P17** (implemented Three-Store baseline), **ADR 0003** (four-store Git Core / Context target), **ADR 0004 / GCTX-M01** (mandatory metadata-only Core), **ADR 0005 / GCTX-M02** (common nominal OID identity), **ADR 0006 / GCTX-M03** (field claims and observation-scoped typed relation groups), **ADR 0007 / GCTX-M04** (verification-aware normal-query policy), **ADR 0008 / GCTX-M05** (Core Git verification / Context Provider assessments / Operational execution), **ADR 0009 / GCTX-M06** (bounded immutable admission evidence distinct from physical health), **ADR 0010 / GCTX-M07** (operation-scoped physical integrity assurance), and **ADR 0012 / GCTX-M08** (append-only alternate physical instances and recovery). Read [ADR 0003](docs/adr/0003-append-only-git-core-and-context-store.md) for explicit supersession of PF-P06/PF-P08's former placement/full-backup assumptions and scoped Search implications, then ADR 0004 for the metadata admission extension. Preserve other accepted decisions; do **not** reopen them by implication. Do not reopen the questionnaire or adopt unchosen cache, collection, checkpoint, Exchange trust, retention/deletion or Git interpretation policies.

Distinguish accepted target design, currently implemented behavior, verified behavior and unresolved boundaries. The checked-out `schema_sql()`, `operational_schema_sql()`, and `search_schema_sql()` and generated DDL fingerprints determine their implemented schemas; a hardcoded version label or old handoff is not proof of current behavior. Never claim full completion from historical receipts or passing focused tests. Three-store physical separation was accepted and integrated through PR #39; the newer four-store/append-only Git Core design and metadata-only requirement are accepted but **not yet implemented**. Neither integration nor a design-only PR implies full release acceptance. No generic result/batch/bundle/member-seal owner or eligibility layer may recreate Publication under another name. Local revision, per-object atomicity, domain scope completeness and physical installation readiness have independent responsibilities.

For documentary status, read the [Phase 2 decision register](docs/phase2/decision-register.md) and [status audit](docs/phase2/documentation-status-audit.md), applying ADR 0004's later scoped override. Reconcile each old question by scope: neither historical "Selection paused" nor an umbrella "Q05–Q12 resolved" overrides explicit decisions. Keep decision status separate from implementation and exact-revision verification. Dated design work sequences are not instructions to repeat completed implementation. CAS-76/CAS-77 remain deferred identifiers needing original-source clarification, not guessed requirements.

## Architecture and domain invariants

**Target-only invariants from accepted ADRs 0003–0010 and 0012:** Git Core represents Git-specific metadata observations/attributes/relationships, permanent repository identity, optional verified canonical object bytes/DAG and actual ref/acquisition observations, and permits no application-visible UPDATE/DELETE/REPLACE (including revision/completion/repair loopholes). Unverified metadata is usable as attributed metadata, not automatically intrinsic byte-verified truth. Context owns authoritative PR/Issue/comment/review/Source/Provider state, its text and conflicts; it is **durable, not Operational or disposable**. Git-only use, including metadata-only cataloging, must not depend on Context. Context may reference Git Core, never the reverse for validity. A full backup of the new target includes **both authoritative stores** when Context data is included; a Git-only backup must say so and distinguish catalog completeness from raw-repository restorability. Keep existing Three-Store code/documentation explicitly labeled *implemented*, not *target*, until replaced. See [table disposition and transition gates](docs/architecture/git-core-context-transition-plan.md). Existing Core text GC debates apply only to future Context text GC; do not introduce Git Core GC.

- Dependencies remain `cli -> application -> domain/ports`; adapters own SQLite, Git/HTTP and filesystem operations.
- `adapters/sqlite/schema.py` composes the packaged production DDL (Core `schema_sql()`, Operational `operational_schema_sql()`, Search `search_schema_sql()`), including generated JSON guards. Initializer, writers, readers, Exchange, maintenance and installed distributions use their exact fingerprints. Fresh format only; no compatibility shim.
- Enable foreign keys and recursive triggers on every connection. Use SQLite snapshots/savepoints and OS `locks/writer.lock`. Do not use immutable connections against mutable catalogs or hold a write transaction over network work. Roll back intended units on body/constraint/COMMIT failure.
- Service, repository and Source-registration UUIDv4 are portable identities; local Source IDs are distinct. Names/URLs do not merge identities. Explicit equivalence/cancellation assertions do not rewrite facts or coverage.
- Absolute times are signed int64 Unix epoch microseconds with `_us` suffixes. NULL is unknown; zero and negative values are valid. Parsing time, receipt order, UUID order and parser version do not establish domain freshness.
- PR attributes, natural-key title/body/conversation documents, independent threads and known Source roster retain latest accepted state with necessary current-field provenance. No normalized full API edit history. Missing differs from explicit null; inherited values retain their original clock/capture/module/version. Genuine equal/incomparable-clock alternatives remain unresolved.
- Ordinary Issue identity is service/provider ID, independent of current repository membership/number. Review identity is PR/kind/provider document ID. Transfer updates membership while preserving capture. Detached captured IDs may survive Exchange without inventing registrations; verify relationships when present. Receiver-local checks advance only on accepted authoritative live acquisition with pre-request revision/scope fences, never sender checks.
- Documents use `(change_request_id, kind, provider_change_request_document_id)`. Exact UTF-8 SHA-256 identifies domain text. No document surrogate/version table or duplicate PR title/body authority.
- Coverage retains exactly five claim columns and explicit typed ownership. The latest observation's candidate set determines current complete/partial/unknown/conflict; no fallback to older complete. Details are advisory. Valid individual resources remain usable when a larger list fails. Empty terminal and no terminal differ; nested required-child and exact head/base evidence must be truthful. Metadata-scope completeness, byte possession and verified closure must not be conflated; new scope contracts remain design work under ADR 0004.
- Source associations are known positive pairs. Partial inventory R1 cannot delete previously known R2. No new negative membership or deletion policy.
- Retain actual provider events and minimal code head/base/role anchors. Current head B cannot borrow an assessment of A or require the entire old PR as provenance.
- Metadata-only Core admission does not require bytes or rehashing. GCTX-M02 selects one common nominal identity keyed by full `(object_format, oid)` and separately attributed, potentially conflicting metadata. The same nominal identity may be referenced across repositories, but never implies repository membership, actual bytes or canonical facts. Later verified representations do not update earlier reports. GCTX-M03 stores scalar assertions separately by field and ordered relationship members within one coherent observation-scoped group; preserve known-empty versus unknown/partial, and never union unrelated parent/tree groups into a purported complete Git structure. Preserve actual OIDs, unknown fields and necessary standalone provenance without fabricating objects or attributing byte proof. For optional verified representations, verify canonical Git format/OID/type/size against physical bytes and install the representation's entire intrinsic structure atomically. Do not let an earlier unverified type/size/parent report block later correct evidence. Retain genuine captures. Reanalysis of retained raw objects is Git-only; explicit decoder differences do not create profile authority or silently rank versions.
- No required API transport originals or replay. Normalize accepted partial GraphQL requirements/continuations/targets in memory. Reject opaque provider replicas and hidden original-bearing pending/job JSON. Optional external recording/warning failures remain nonfatal with bounded allowlisted diagnostics.
- Shared CAS admits only explicit real Git representation. The **implemented baseline** still shares Provider domain text with Git bytes in the Core, but **ADR 0003's target moves Provider text into Context** and retains admitted verified Git bytes in append-only Git Core. ADR 0004 makes raw-object acquisition optional, not previously retained bytes disposable. Preserve domain text, raw Git integrity, quarantine and actual canonical Git repair authorization; design recovery without in-place Core mutations. CAS-41 checks verified copied-database physical quarantine count before restore diagnosis. Intentional metadata-only nonacquisition is not physical corruption; actual corruption must not be reclassified as optional absence. Restore validates in a fresh stage and publishes atomically without overwrite. No physical retained-data cleanup or new GC policy.
- Exchange resolves direct typed resources/dependencies from a consistent snapshot. Transport envelope/idempotency records do not own admitted domain validity. Keep real missing/conflicting candidates, handle reverse/repeat/late promotion/onward export, and do not infer broad complete closure from partial arrival or authenticate provider completeness from sender digests alone. The new metadata-only path must preserve metadata/provenance without fake payloads or sender-verification promotion.
- In the implemented Three-Store baseline, `local_revision` is the single receiver-local counter for paging/fences and `advance_local_revision` replaces the old mechanical publish call. The ADR 0003 target **must replace this mutable Core counter with an append-only-safe/fenced design**. No counter-history table or sender-revision freshness import.
- Jobs freeze Source registrations and nonsecret settings. Resume resolves credential references at execution. Operational progress/cache deletion cannot invalidate admitted domain facts. Cache loss requires a genuine safe fetch or reuse-unavailable outcome for byte-dependent work, not hidden fetching for ordinary metadata queries; no fabricated remote observation.

LFS pointer bytes and attachment source text/URLs retain existing meanings; automatic external body fetching, broader deletion propagation, transport recording retention and CAS-76/CAS-77 remain deferred.

## Implementation, review and acceptance

For substantial architectural changes, record owner-approved decisions in a focused ADR/design PR, then implement coherent stacked PRs. Use independent subagents and executable counterexamples for the affected boundaries; the four-scope review requirement applies to the large Schema 20 redesign and other tasks that explicitly require it, not automatically to a prose fix. Reviewers must not approve their own production changes. For material findings, fix the root cause, add a regression and re-review affected paths.

**Development validation vs release acceptance:** Ordinary development relies primarily on local testing. Run relevant focused tests during editing, expanding scope according to dependencies and actual correctness risks; do not require a complete local test suite after every edit or for every intermediate PR. Ordinary development CI in GitHub Actions executes inexpensive static/lint/format checks, repository/CI configuration validation, and smoke tests, inspecting supplied local evidence and reporting validation gaps without automatically running the full test suite or duplicating locally verified tests. A passing development CI run confirms that development checks passed (`selected_checks_only` or development checks passed); it does not claim complete runtime test acceptance. Complete dual validation (full independent pytest locally AND in hosted CI, isolated wheel/sdist packaging, schema/integrity checks, and exact test-node reconciliation) is required only for an explicit, user-invoked release-validation operation. An explicit release validation does not authorize release, deployment, publication, tagging, or merging. Preserve meaningful behavior tests; retire obsolete mechanism assertions only with explicit replacement-node mapping. Report real versions, failures, skips, exclusions and unexecuted tests.

Use one controlled workload at a time for comparative performance; concurrent test timings are not sequential benchmark evidence. Historical reports remain intact. Update active docs for materially changed behavior. Submit actual PR dependencies and review findings. Merges require explicit authorization for the named stack and independent verification of integration ancestry and effective trees.

## Reuse lessons as repository Agent Skills

Repository-local skills live in `.agents/skills/<skill-name>/SKILL.md` with YAML `name` and `description`; optional `references/` and `scripts/` belong beside the skill. At task start, discover and read **relevant** skills rather than loading every skill. Agents without automatic skill discovery should consult this directory explicitly. Skills describe reusable procedures, not policy changes or additional tool permissions.

**Actively capture a verified, generalizable lesson** when the same root cause causes repeated failed attempts, an independent review exposes a non-obvious failure mode, or a hard-won workaround/procedure would prevent another agent from repeating the investigation. Prefer improving an existing skill over creating overlapping ones. At a stable checkpoint and before handoff, use `$lessons-to-skills` to evaluate such lessons. Record symptoms, root cause, verified fix, reproduction/check commands, applicability, counterexamples and relevant source links. Prefer small scripts for repeatable deterministic checks. Avoid speculative recipes, one-off task logs, unverified PASS claims, private data and credentials. Do not convert an unresolved architecture decision into a skill requirement.

When authorized to edit the task branch, commit applicable skill additions/updates alongside the relevant correction or in a clearly dependent documentation PR. A reviewer working read-only may recommend skill changes but must not mutate the reviewed tree. Validate skill frontmatter, links and executable helpers; include skill changes in the review and report what was learned in the final handoff. If there is no reusable verified lesson, do not create a placeholder skill. See [OpenAI's repo-local skills practice](https://developers.openai.com/blog/skills-agents-sdk) and `docs/change-aware-ci.md` for appropriate CI selection.
